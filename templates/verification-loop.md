# AI 검증루프 v1

v1 · 2회차 — 오늘 바뀐 점
- 판정은 `templates/approval-checklist.md` v1 의 [반려] 항목 기준으로 하고, "아니오"가 나온 항목 문장을 근거로 인용한다.
- 행안부 「소프트웨어 개발보안 가이드」(2021) 구현단계 보안약점 검토 표 작성을 절차와 출력 형식에 넣었다.
- 판정 기준 절의 "충분한가 · 적절한가" 문장을 체크리스트 v1 항목 참조로 바꿨다.

AI 가 만든 변경분과 외주사 PR 을 머지하기 전에 거치는 절차다. **만든 쪽과 검증하는 쪽을 분리**하고, 판정은 `templates/approval-checklist.md` 의 네 기준으로 한다.

## 1. 왜 분리하나

만든 세션은 자기 코드를 옹호한다. 같은 컨텍스트 안에서 "잘 됐는지 확인해 주세요"라고 물으면 만든 이유를 다시 설명받을 뿐이다. 검증은 **변경분만 보는 새 컨텍스트**에서 한다.

## 2. 패턴

| 패턴 | 방법 | 쓰는 때 |
|---|---|---|
| 만든 세션 → 리뷰 세션 | 새 터미널에서 Claude Code 를 새로 띄워 diff 만 보게 한다 | 기본. 모든 변경 |
| Claude 생성 → 다른 모델 리뷰 | 새 터미널에서 `claude --model sonnet` 처럼 다른 모델로 새 세션을 띄워 같은 diff 와 체크리스트를 넘긴다 | 중요한 변경의 교차 검증 |
| 리뷰어 Sub-agent | 읽기 전용 리뷰어를 `.claude/agents/` 에 정의해 두고 위임한다 | 같은 세션 안에서 격리된 컨텍스트로 리뷰할 때 |

## 3. 역할

| 역할 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 만든 세션 | 구현, 테스트 작성, 리뷰 결과 반영 | 자기 변경의 승인 판정 |
| 리뷰 세션 | diff 읽기, 체크리스트 대조, 테스트 실행, 이슈 목록과 판정 | **코드 수정.** 고치기 시작하면 그 순간 "만든 쪽"이 된다 |
| 사람 | 요청 범위 확정, 리뷰 이슈의 수용 · 기각, 최종 머지 | 리뷰어의 판정을 읽지 않고 머지 |

## 4. 절차

1. **요청 범위 확인.** 무엇을 요청했는지 한 문장으로 받는다. 범위가 주어지지 않았으면 판정하지 말고 먼저 묻는다.
2. **변경 파일 목록과 diff 읽기.** `git diff --stat <범위>` 로 목록을 먼저 보고, 파일마다 diff 를 읽는다. patch 파일이면 `git apply --stat` 으로 목록을 뽑는다.
3. **체크리스트 대조.** `templates/approval-checklist.md` 를 읽고 항목마다 예 · 아니오 · 확인 필요 중 하나로 답한다. [반려] 항목이 "아니오"면 그 항목 문장을 그대로 인용해 근거로 남긴다.
   - **3-1. 행안부 검토.** 변경분을 행안부 「소프트웨어 개발보안 가이드」(2021) 구현단계 보안약점 기준으로 검토해 항목 · `파일:줄번호` · 판정 표를 만든다. 해당 항목이 없으면 "해당 없음"이라고 적는다.
4. **테스트 실행.** 변경된 모듈의 테스트만 실행한다. 어느 명령을 쓰는지는 팀 `CLAUDE.md` 의 빌드 · 테스트 명령을 따른다. 결과는 통과 · 실패 수와 실패한 테스트 이름만 남기고 전체 로그를 대화에 싣지 않는다.
5. **판정.** 네 기준(테스트 통과 / 치명 이슈 0건 / 요청 범위 이탈 없음 / 컨벤션 준수)을 하나씩 판정한다. 기준 안의 [반려] 항목 중 "아니오"가 하나라도 있으면 그 기준은 미충족이고, 미충족 기준이 하나라도 있으면 반려. [경고] 항목은 판정에 쓰지 않고 이슈 목록에 경고로 남긴다.
6. **되돌리기.** 리뷰 결과를 만든 세션에 넘긴다. 만든 세션은 이슈마다 수용 · 기각을 사람과 정한 뒤 수용한 것만 고치고, 다시 2번부터 돈다.

## 5. 출력 형식

```
판정: 승인 | 반려

| 기준 | 결과 | 근거 |
|---|---|---|
| 테스트 통과 | 충족 / 미충족 | 실행 명령과 통과 · 실패 수, "아니오"가 나온 항목 문장 |
| 치명 이슈 0건 | 충족 / 미충족 | 치명 이슈 번호, "아니오"가 나온 항목 문장 |
| 요청 범위 이탈 없음 | 충족 / 미충족 | 요청 문장 vs 변경 파일 목록, "아니오"가 나온 항목 문장 |
| 컨벤션 준수 | 충족 / 미충족 | 위반 항목 번호, "아니오"가 나온 항목 문장 |

행안부 구현단계 보안약점 검토
| 항목 | 파일:줄번호 | 판정(취약 / 양호 / 해당 없음) |
이 검토는 사람이 읽는 수동 검토이며 Sparrow 정적 분석 결과를 대신하지 않는다.

이슈 목록
| # | 심각도 | 파일:줄번호 | 근거 | 수정 방향 |
```

- 이슈 한 건은 심각도(치명 / 경고 / 제안) · `파일:줄번호` · 근거 · 수정 방향 네 항목을 모두 채운다.
- 근거 줄번호를 댈 수 없는 지적은 이슈로 올리지 않고 "확인 필요"로 따로 적는다.

## 6. 판정 기준 (v1)

판정 문장은 모두 `templates/approval-checklist.md` v1 의 항목을 그대로 쓴다. 여기에는 기준별로 어느 절을 보는지만 적는다.

- 테스트 통과 — 1절. 새 public 메서드(getter · setter · 생성자 · record 접근자 제외)와 새 엔드포인트마다 테스트 메서드가 1개 이상 있는지 본다.
- 치명 이슈 0건 — 2절. 행안부 보안약점 "취약" · 비밀값 노출 · 데이터 손실 · 인증 우회 · SQL 문자열 조립 다섯 유형만 치명이다.
- 요청 범위 이탈 없음 — 3절. 요청 기능 밖 변경은 요청 기능 파일 안의 import 정리만 허용한다.
- 컨벤션 준수 — 4절. 계층 규칙 위반 · 빈 catch · `System.out` 류는 반려, 네이밍과 그 밖의 §2 항목은 경고다.

## 7. 하지 말 것

- 리뷰 세션은 코드를 수정하지 않는다. 보고만 한다.
- 테스트를 실행하지 않고 "통과"라고 쓰지 않는다. 실행할 수 없었으면(서버 꺼짐, 의존성 미설치) 그 사실을 적고 사람에게 기동을 요청한다.
- 요청 범위를 모르는 상태에서 "범위 이탈 없음"을 충족으로 표시하지 않는다.
- 이슈 0건이 나오면 "경고 · 제안 수준까지 다시 봐 달라"고 한 번 더 요청한다. 0건은 결과일 수도, 안 본 것일 수도 있다.
