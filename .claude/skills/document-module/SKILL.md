# 레거시 모듈 문서화

- **분석 대상 폴더(`legacy/…`)의 파일은 읽기만 한다.** 수정 · 이동 · 포맷팅 · 실행 결과물 생성을 하지 않는다.
- 산출물 폴더 `<모듈명>` 은 폴더 이름이 아니라 아래 표로 바꾼 이름이다. 표에 없는 경로면 멈추고 묻는다.

| 모듈 경로 | `<모듈명>` |
|---|---|
| `legacy/item-bank-php` | `item-bank` |
| `legacy/assignment-thymeleaf` | `assignment` |
| `legacy/grade-mssql` | `grade` |

- 산출물: `docs/<모듈명>/ARCHITECTURE.md` · `ERD.md` · `BUSINESS-RULES.md`. 각 문서 머리에 분석 범위, 근거 경로 기준(예: `legacy/item-bank-php/` 기준), "코드를 읽기만 했고 실행해 확인하지 않음"을 적는다.
- 근거는 모두 `파일:줄번호`. 직접 열어 확인하지 못한 것은 "미확인"으로 둔다.

## 절차 — 단계마다 결과를 파일에 저장한 뒤 다음 단계로 넘어간다

1. **계획 제시.** 파일 목록과 줄 수, 분석 범위(두 번째 인자가 있으면 그 범위만), 단계별로 채울 문서 · 절을 먼저 보여 준다. 파일은 아직 쓰지 않는다.
2. **진입점.** URL · 화면 · 컨트롤러 · 배치 · 프로시저 등 외부에서 들어오는 지점과 요청 방식을 찾는다. → `ARCHITECTURE.md` 개요 · 폴더 구조 · 진입점 절 저장.
3. **의존 관계.** include · import · 함수 호출 · 외부 라이브러리 · DB 접속 지점을 따라가 호출 방향을 그린다. 호출은 실제 호출 줄을 열어 확인한다. → `ARCHITECTURE.md` 의존 관계 절 저장.
4. **데이터 흐름.** 읽고 쓰는 테이블 · 뷰 · 컬럼, SQL 종류(SELECT/INSERT/UPDATE/DELETE), 트랜잭션 경계를 정리한다. 스키마는 `db/` 아래 DDL 에서 확인한다. 비교 · 필터에 쓰는 컬럼은 컬럼 단위 `COLLATE` 유무까지 확인하고(없으면 테이블 기본값과 두 줄 모두 인용), 날짜 · 시각 컬럼은 코드에서 어떤 타입으로 바뀌어 무엇과 비교되는지, 시간대 기준(DB · JVM)을 적는다(확인 못 하면 "미확인", docs/assignment BR-05 · BR-15). → `ERD.md`(테이블 목록 · 관계 · 진입점별 읽기/쓰기) 저장.
5. **비즈니스 규칙 후보.** 조건문 · SQL · 검증 코드에서 규칙을 뽑아 아래 형식으로 적는다. → `BUSINESS-RULES.md` 저장.
   - 예외 처리 규칙은 코드가 직접 던지는 예외뿐 아니라 프레임워크가 경계에서 던지는 예외(트랜잭션 시작 시 커넥션 획득 실패 · 커밋 실패 등)도 목록에 넣고, 각 예외 타입의 상위 클래스를 확인해 어느 `catch` · 전역 핸들러에 걸리는지, 아무 데도 안 걸리는지 적는다(docs/assignment BR-13: `CannotCreateTransactionException` 은 `DataAccessException` 이 아니다). 전역 핸들러의 응답 HTTP 상태도 적는다.
   - 규칙 하나 안에 코드로 확인한 분기와 프레임워크 · DB 기본 동작에 기댄 부분이 섞이면 확신도를 `확실(…) / 추정(…)` 으로 나눠 적는다.
6. **표본 점검 추천.** 사람이 코드와 직접 대조할 규칙 3개를 골라 답변에 적는다(아래 참고).

## 규칙 형식 (`BUSINESS-RULES.md`)

```markdown
### BR-01
- 규칙: <한 문장. 조건과 결과를 함께>
- 근거: `search.php:85`, `search.php:97-98`
- 근거 코드:
  ```php
  $q = trim($q);
  $where .= " AND (title LIKE ? OR stem LIKE ?)";
  ```
- 확신도: 확실 | 추정
- 비고: <예외 · 다른 화면과의 차이 · "주석만 있음" 등>
```

- 확신도: **확실** = 조건문 · SQL 로 확인 / **추정** = 이름 · 주석으로 짐작.
- 코드에 있는 것만 규칙으로 올린다. 주석에만 있는 내용은 비고에 "주석만 있음"으로 남긴다.

## 하지 말 것 (docs/item-bank 검증 이력에서 실제로 틀렸던 유형)

- **조건을 부풀리지 않는다.** "하나라도 실패하면 모두 롤백"(BR-36)은 틀렸다. 실제로는 `execute()` 가 false 일 때만 예외를 던져 롤백했다. 예외 · 롤백 규칙은 무엇이 던지고 무엇이 잡는지, 에러 리포팅 설정(`MYSQLI_REPORT_OFF` 등)까지 확인하고 그 범위만 적는다.
- **"허용 목록이 아니면 경고" 식으로 분기를 뭉뚱그리지 않는다**(BR-17). 빈값 · 기본값 · 알 수 없는 값이 각각 어느 `case` 로 가는지, 경고가 나는지 따로 적는다(BR-16, BR-22 의 빈 `page`).
- **입력 정규화를 빠뜨리지 않는다.** 비교 전 `trim` · 소문자 변환, 무시되는 파라미터(`dir`), `===` 와 DB 콜레이션(`_ci`) 비교 차이를 규칙이나 비고에 넣는다(BR-16, BR-13).
- **부수 동작을 빠뜨리지 않는다.** 채번 `FOR UPDATE`, 로그 기록 같은 줄도 근거에 넣는다(BR-36).
- **떨어진 줄을 한 덩어리 인용으로 이어 붙이지 않는다.** 줄이 떨어져 있으면 줄번호 주석과 함께 나눠 인용한다.
- **주석을 근거로 쓰지 않는다.** 주석과 코드가 다르면 코드가 기준이다(BR-08: 주석은 "전체", 코드는 `level < 5`).
- **뷰 · 공통 함수는 정의까지 연다.** 뷰 이름만 보고 필터를 짐작하지 않는다(BR-14: `v_item_public` 의 `WHERE i.status = 'A'`).
- 존재하지 않는 함수 · 파일을 적지 않는다. 적기 전에 Grep 으로 정의 줄을 찾는다.
- 호출 방향을 이름으로 추측하지 않는다. 호출하는 줄을 근거로 단다.
- 코드에 없는 규칙(일반적인 도메인 상식, "보통 이렇다")을 만들지 않는다.

## 마지막 단계 — 표본 점검 추천

답변 끝에 사람이 코드와 직접 대조할 규칙 3개를 표(ID · 고른 이유 · 확인할 `파일:줄번호`)로 추천한다.

- 1개는 **가장 그럴듯한 규칙**(읽으면 당연해 보여 검증 없이 넘어가기 쉬운 것)이다.
- 나머지는 확신도 "추정", 예외 · 롤백 · 기본값 분기처럼 위 "하지 말 것" 유형에 걸리는 규칙에서 고른다.
- 점검 결과는 `BUSINESS-RULES.md` 끝 "검증 이력" 표(날짜 · 규칙 · 조치 · 내용)에 사람이 적도록 빈 표를 만들어 둔다.
